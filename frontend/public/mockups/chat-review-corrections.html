Trade-offs
  • Feels additive rather than rejective — mentally lighter.
  • Uses more real estate. Adds a second input right above the main one. Some CPAs will confuse the two.
  • Best used AS A COMPLEMENT to B, not a replacement. Ship B first, add C only if telemetry shows CPAs want to refine rather than retry.

A + B combined — my recommendation to ship first. When AI is uncertain → asks (Option A). When AI is confident but wrong → user clicks "Not quite" (Option B). Covers both failure modes.

Path B — AI confident but wrong

"these are ATM cash deposits from the owner"

I'll book these to Bank Deposits — looks like standard deposit activity.
Click "Not quite" → chat refocuses, AI knows to avoid Bank Deposits. Next reply almost always right.
Why both, not either
Two failure modes, two fixes. If the AI is unsure, it should ASK (A). If the AI is sure but wrong, the user should reject with context (B). Together they turn every failed proposal into a learning moment for the LLM, without adding a rejection ceremony.
Total effort: ~15 lines backend prompt + ~30 lines frontend. Under an hour.
Wins: higher first-shot accuracy (A), single-click correction path (B), LLM improves within the same card.
