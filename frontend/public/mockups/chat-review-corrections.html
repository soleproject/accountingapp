Option A — what if the user doesn't agree with the clarify, or wants to add more info? The clarify block always has BOTH quick-pick chips AND a free-text input. The user can (a) answer with a chip, (b) type a corrective reply, or (c) reject the question outright. Every user reply gets fed back to the LLM as another turn — the AI can either commit to a proposal OR ask again with a sharper question.

Edge case — AI asks again
If the user's reply introduces new ambiguity ("actually some are rent, some are security deposits"), the LLM returns ANOTHER clarify instead of a proposal. All prior turns stay visible above. The chat continues until either the AI commits to a proposal OR the user says "just book it as X".
There's no hard turn limit — but in practice 90%+ of cards resolve in ≤2 turns (chip → done, or refine → done).
Under the hood — where the "disagreement" gets stored
• Every user reply (chip or typed) gets pushed into priorQAs on the frontend.
• On every subsequent propose call, the entire priorQAs array ships to the backend as prompt context.
• The LLM sees the full mini-conversation and produces its next response accordingly — either a proposal or another clarify.
• When the user finally clicks Confirm & book, the last user reply becomes the "learned rule" (checkbox above).
A + B combined — my recommendation to ship first. When AI is uncertain → asks (Option A). When AI is confident but wrong → user clicks "Not quite" (Option B). Covers both failure modes.

Why both, not either
Two failure modes, two fixes. If the AI is unsure, it should ASK (A). If the AI is sure but wrong, the user should reject with context (B). Together they turn every failed proposal into a learning moment for the LLM, without adding a rejection ceremony.
Total effort: ~15 lines backend prompt + ~30 lines frontend. Under an hour.
Wins: higher first-shot accuracy (A), single-click correction path (B), LLM improves within the same card.
